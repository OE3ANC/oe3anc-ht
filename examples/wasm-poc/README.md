# C62 WASM investigation and host proof of concept

Investigated 2026-10-15 against project baseline `9e6345028e2439d90b9c2469aae50eb75d48ac73`.
This example is independent of the firmware build. It does not enable a service,
change audio routing, or access hardware.

## What the firmware contains

These are two different firmware families; do not interchange their DSP images.

| Image | Static evidence | Conclusion |
| --- | --- | --- |
| Attached stock C62 full flash, 4,194,304 bytes | No `\0asm`, `\0aot`, `LSHD`, `WasmService`, `wasm_runtime_load`, `wamr_hifi4`, or `aot_loader.c` matches | No evidence that stock firmware uses WASM; absence of signatures cannot exclude stripped/compressed code |
| Project original DSP image, 466,832 bytes | WASM service, WAMR HiFi4 source paths, AOT loader/runtime and native bindings | Includes WAMR-derived DSP runtime code; actual service execution remains untested |

Offsets below are file offsets, not CPU addresses. Stock strings include
`nn_denoise_floor` at `0x103eef`, `set_cae_denoise_param` at `0x1733e0`, and
`set_white_noise_state` at `0x173440`. These suggest a native proprietary
enhancement path; they do not establish its algorithm, activation or audio quality.

The original project DSP contains `WasmService_initialize` at `0x63cb`,
`WasmService_App_onSet` at `0x6454`, a run-main diagnostic at `0x64c5`, and
`aot_loader.c` at `0x747a` within a `cp_6012_nano/modules/wamr_hifi4/` source path.
It also contains `set_model`, `set_input`, `get_output` and Thinker service
diagnostics. The native-symbol table at `0x5dea0` exposes ten Thinker functions,
including `tModelInit`, `tSetInput`, `tForward` and `tGetOutput`.
This is a possible neural-inference bridge, not proof of an installed denoiser.

AOT support is strongly evidenced. Raw WASM interpreter support and the exact
runtime revision are not established. Some `\0aot` byte matches are merely a
string terminator followed by an `aot_*` name; magic matching alone does not
identify embedded modules. Static analysis does not prove runtime execution.

## Reproducing the small proof of concept

From the repository root:

```sh
python3 examples/wasm-poc/build.py
```

The default uses the existing emsdk's Clang directly, without Emscripten's JS
runtime or libc. Alternatively specify `--clang /path/to/clang --node /path/to/node`;
Clang needs its WASM linker. No additional package is installed by the script.

`gain.c` exports a probe returning 42, `main()` returning success, a pointer to
a fixed 480-sample mono PCM16 buffer, and an in-place Q15 attenuation function.
Counts 0–480 and gains 0–32768 are accepted; invalid requests return -1 before
mutation. Integer division rounds toward zero. There are no imports, heap
allocations, threads, SIMD or OS calls. Linear memory is fixed at 64 KiB, including
an 8 KiB auxiliary stack. This is our proposed example ABI, not a recovered DSP ABI.

The build uses `--target=wasm32 -mcpu=mvp -nostdlib` and explicit exports. Its
Node test executes the actual WASM, checking probe/main, imports, fixed memory,
silence, unity, half gain, PCM extrema, odd negative values, 80/320/480-sample
blocks, untouched tails and invalid inputs. It is a transport/arithmetic proof,
not an audio enhancement algorithm or DSP performance benchmark.

Observed with installed Clang 22 (`c4e1bca407f4cca7644937c117890fad157fec4b`):
262-byte `build/wasm-poc/gain.wasm`, SHA-256
`bc28446de891c76c49ac9d40f1d63b0a5469018fe77a126b22d94125a970669a`.
All host checks passed. This verifies Node execution, **not WAMR or C62 execution**.

## How to get this onto the DSP

The old OpenRTX C62 host integration provides
[`lsf_wasm_load_app`](https://github.com/OE3ANC/OpenRTX-c62/blob/33059fd6a2631bb1bdf98dc4d9916886a57d1e44/platform/targets/c62/services/service_wasm.c).
It sends property 0 to service 2 after reading this container:

```text
"LSHD" | uint32 little-endian payload length | payload
```

The wrapper forwards the payload; it does not itself decide whether bytecode or
AOT is supported. Its original bounds checks are insufficient: a future port
must require at least eight bytes, use unaligned-safe reads, and check payload
length against `buffer_size - 8`. Do not copy the old wrapper unchanged.

The public WASM wrapper only loads an application. It does not expose arbitrary
function calls or automatically place `process()` in AudioFlinger. The DSP's
main diagnostic suggests a load-and-run-main lifecycle. Thinker has a separate
input/output bridge, but exact exported function signatures, buffer ownership,
pointer translation and lifetime must be recovered before using it for PCM.

The practical next on-device experiment is:

1. Establish the exact DSP WAMR version/configuration, whether bytecode works,
   and a matching HiFi4 AOT compiler invocation. Ask ListenAI for a known-good
   minimal module and its build recipe if these cannot be recovered locally.
2. Restore a bounded host loader behind an opt-in diagnostic configuration.
   Keep the pinned 48 kHz host/DSP pair and memory reservations. Confirm module
   storage is DSP-visible, correctly translated and coherent, and remains alive
   for the runtime's required lifetime; do not assume an arbitrary ARM pointer works.
3. First run a deterministic self-test with an observable returned result.
   A successful load is insufficient proof that `main()` executed. Establish
   the result channel first: UART printf is bypassed in our normal DSP image.
   Do not re-enable DSP UART logging on the companion/PTT pins as a shortcut.
4. Establish a bounded PCM input/output call, then compare synthetic blocks
   against the host results. Measure worst-case latency, memory and failures
   while normal audio is active before trying a real filter.

Use preallocated buffers and a worker with explicit ownership and deadlines.
Keep RPC, allocation and logging out of audio callbacks. A missed enhancement
deadline should bypass enhancement; cancellation must discard stale results.
The existing RF/PTT shutdown paths must remain independent. No hardware was
flashed or keyed in this investigation.

## Toolchain research

[WAMR's application guide](https://github.com/wasm-micro-runtime/wasm-micro-runtime/blob/main/doc/build_wasm_app.md)
documents Clang/WASI-SDK compilation and explicit exports. A freestanding,
import-free module is the smallest first step. Adding WASI dependencies would
require imports that this closed runtime may not provide.

[ListenAI's WAMR fork](https://github.com/LISTENAI/wasm-micro-runtime) has
`main`, `xos`, `freertos` and `build-wamrc-xtensa` branches. At inspection,
`build-wamrc-xtensa` was `e31fa92b6efb50737371a09cfaa9f9889de4e79d` and `xos`
was `e89a856c330a25e1c9b84e79a4f4e69f48682a2e`.
Its [compiler workflow](https://github.com/LISTENAI/wasm-micro-runtime/blob/e31fa92b6efb50737371a09cfaa9f9889de4e79d/.github/workflows/build-wamrc-xtensa.yml)
builds LLVM with Xtensa support and then `wamrc`.
The [LLVM builder](https://github.com/LISTENAI/wasm-micro-runtime/blob/e31fa92b6efb50737371a09cfaa9f9889de4e79d/build-scripts/build_llvm.py)
uses Espressif LLVM's `xtensa_release_13.0.0` branch. The XOS branch has an Xtensa
relocator and soft-float helpers, consistent with strings in our DSP image.

Candidate pipeline: C → portable `.wasm` → compatible Xtensa `wamrc` → `.aot`
→ LSHD container → host loader. A generic Xtensa/ESP32 binary is not yet a
verified HiFi4 artifact. CPU features, calling convention, relocation support
and AOT format version must match; no exact working AOT command is claimed here.
The DSP itself contains a recommendation to use `wamrc --size-level=0` for
literal islands. That is a compatibility clue, not a complete build recipe.

## Longer-term receive audio enhancement

Current FM receives demodulated radio PCM through the 48 kHz DSP transport and
passes it through `fm_queue` in `modules/audio/service.cpp`. Enhance the speaker
branch only, after FM demodulation. Preserve squelch and tone-detection behavior.

M17 decodes a payload into 320 speech samples and sends them to the speaker in
`modules/modes/m17.cpp`. The speech rate is 8 kHz (40 ms per 320-sample block).
Enhancement belongs **after Codec2 decode**, not on M17 modem/discriminator
samples. The current audio service expands lower-rate speaker samples by
repetition to the 48 kHz transport. A shared 48 kHz speaker processor is possible,
but low-rate processing before interpolation saves work; better resampling is a
separate audio-quality consideration.

Start with bypass/attenuation to prove block transfer, then a modest high-pass
or EQ filter with measurable results. Benchmark a native ARM version as a
baseline: WASM adds programmability, not automatic speed or better audio.
FM background noise and Codec2 synthesis artifacts need different evaluation
material and may need different processing.

[RNNoise](https://github.com/xiph/rnnoise) is a later candidate: its documented
example expects 48 kHz mono PCM16. Its feasibility on this DSP, runtime cost and
benefit for Codec2-decoded speech are unverified. Upsampling narrowband speech
does not restore missing information. Use recorded FM and decoded M17 speech
with level-matched bypass comparisons before claiming intelligibility gains.

Remaining acceptance gate: a module executed on the actual pinned DSP, a proven
PCM/result ABI, and measured processing deadlines under receive load. The host
example intentionally does not pretend to satisfy that gate.
